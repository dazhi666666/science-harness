# 温室实验规程

English | [中文](README.md)

## 对照条件

对照使用相同的书生 Intern-S2、256000 token 容量、输出设置、原生压缩策略、凭据池、环境 JSON、时钟速度、初始资源与领域工具。单 Agent 可以使用所有种植舱并同时提交设备操作；由于只有一个 Agent，其模型调用仍然串行。团队划分种植舱职责，并通过 Router 交换真实引用。不能给团队更强模型、更多水、更快时钟或独占凭据额度。配对试验分开执行，避免争用同一模型服务，并交替顺序重复；服务故障作为可能的混杂因素记录。

先在三任务基线中建立真实模型完成任务的证据，再使用扰动与重复任务发布，考察委派、共享设备竞争、跨舱依赖、传感器诊断及持续值守。脚本运行只验证执行机制。失败、交接未完成或值守不佳均保留记录，不能把失败试验改写成成功重启。

## 重复工作负载

从仓库根目录生成全新场景：

```sh
python3 integrations/ai4science/greenhouse/make-scenario.py .ai4science/greenhouse-long/scenario.json
```

默认每 30 个逻辑分钟发布一批三项实验，共八批，每个模拟步对应一分钟真实时间，最后一批在第 210 分钟到达。每批包含独立的 A 舱光照、B 舱灌溉及 C 舱参考实验；C 必须引用同批 B 的检测。共享供电下降、轮换的传感器偏移与正常水分流失持续要求协调和值守。时间表只发布工作，不是宿主截止时间。最后一批发布后宿主与 Agent 继续运行，不增加 token、请求或总运行时长上限。`--batches`、`--interval-ticks` 和 `--tick-ms` 可准备更大或加速的工作负载，无需改变运行时。

两种模式使用现有安装器和完全相同的场景。`--mode multi-agent` 创建原生团队，`--mode single-agent` 创建唯一根成员。使用不同运行目录，提供相同的 `--base-url`、`--api-key-env` 与重复的 `--extra-key-env` 参数。安装器记录凭据引用，不记录 Key 值。直连网络与启动入口见[运行参考](../README.zh.md)。

## 观测指标

保留环境／设备日志、执行数据库、不可变产物、原生 Session、Router 任务板、生成的 profile 以及带时间的前端截图，明确每轮的模型来源。测量实验完成量、任务发布到分析的延迟、真实结果投递／读取回执、真实活动时间戳、资源冲突、重复动作、人工介入、运行越界、请求重试与 token 用量。记录值守观测区间；后来截图看到宿主仍运行，不能证明该区间一直有效值守。

使用 `verify.py` 独立核验任务、动作与产物的关联证据；[核验参考](../README.zh.md) 定义了可接受的原生输入通道和单独报告的通信观测。`compare.py` 读取两个已安装的运行目录，报告完成模拟步、各路由 token、重试、人工设备提交及压缩事件数；匹配检查失败时拒绝把它作为描述性的真实模型对照。匹配条件包含已记录的源码哈希、实际模型／压缩策略及所有成员实际共享工具声明的并集。按角色分配工具是架构的一部分；单 Agent 保留相同的总体执行能力。仅在两个宿主都停止并完成检查点后使用 `--offline`；只停止一方时，使用 `--single-offline`／`--multi-offline`。通过 `--output` 保存的报告，可由安装时指定 `--comparison-file` 的 profile 展示；表格包含观测长度，并标明对照条件是否通过。一组配对只描述这两轮，不是统计结论，也不自动断言架构优越性。不评分科研结论。

## 上下文压缩

自然容量试验保留声明的 256K 容量，观察实际 `compaction/start`、`compaction/summary` 与 `compaction/end` 事件。确定摘要前未完成的任务，并检查之后的工具调用、找回的操作 ID、完成的分析及实际参考引用。配置了压缩插件、累计 token 账单很大或单次压缩事务成功，都不能独自证明续接有效或信息丢失。

独立的低阈值测试可提前触发相同的原生压缩机制。`install-multi.py --compaction-policy <file>` 将明确的原生配置覆盖项合并到常规策略，并记录实际生效值。测试文件可将 `thresholdRatio` 设为 `0.04`、`retainTokens` 设为 `1024`，仍保留模型声明的 256K 容量；原生配置校验继续生效。但须明确标注实际阈值，并给两种模式相同设置；不能代替自然达到 256K 的结果。比较待办、依赖与已完成设备工作的恢复，包括不必要的重复和人工介入。两种模式都能使用 `greenhouse_history` 与 Router 任务板。不能刻意削弱单 Agent 的记忆制造优势。

## 结果解释

预期收益来自持续环境变化下并行工作的分工，以及较小的角色历史。证据须在考虑模型服务不稳定、物理设备串行、协调开销与压缩恢复后体现该收益。消息更多、Agent 更多或脚本跑得更快都不充分。成功与失败试验一起报告，并附实际界面截图及明确模型来源的记录。
